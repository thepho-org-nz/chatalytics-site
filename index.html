What it does

Answers, not just numbers

Every answer arrives with its working, its context and a way to check it — because in health data, a confident wrong number does more harm than an error message.

Ask in plain English

No query language, no hunting through dashboards. Ask in your own words and get a number, a chart, and the exact code that produced them.

It shows its working

Every answer ships the queries behind it, the as-at date of the data, and any caveat that applies. A wrong number is findable, not hidden.

Questions no dashboard can answer

Join funding, claims, clinical activity and reference data in a single question — the cross-source analysis a fixed dashboard was never built to give you.

Charts you can interrogate

Charts render live and interactive, validated against a strict house standard — never a flat image. Export the underlying data whenever you need it.

Guardrails against known traps

Health data misleads in specific, repeatable ways. Those traps are encoded as structural guards, so the common wrong answers are hard to produce in the first place.

Measured, not assumed

Accuracy is tested against a curated set of known-correct and deliberately adversarial questions — so quality is a number you can see, not a promise.

Cost transparency

Every answer is costed the moment it's produced and rolled up by team — so running the service never ends in a surprise bill.

Model choice, labelled

Choose the processing option that fits your governance. Every answer is labelled with where it was handled, so there's never a question about it later.

Trust by design

Security & privacy as architecture

These aren't settings you switch on. They're structural choices that make the unsafe outcome hard to reach — the right way for sensitive health data to be handled.

De-identification by design

The analyst never sees identifiable data. Columns are allow-listed explicitly; direct identifiers, fine-grained geography and free text never leave the source. Dates are coarsened and ages are top-coded.

No identifiers reach the model

Isolation by architecture, not by query

A tenant's data boundary is enforced by what a session can physically reach — resolved from a verified identity and pinned for the whole conversation — not by a filter the model is trusted to write. Anything unexpected fails closed.

Fail-closed by default

Small numbers stay private

Small-cell suppression and strict result limits mean individuals can't be re-identified through tiny counts, and bulk data can't be siphoned out through an answer.

Suppression + egress limits

Data sovereignty you can prove

Processing stays within your chosen region by default, verified at the moment of use — and every answer records where it ran, so "was any of this handled offshore?" still has an answer months later.

Region-verified + recorded

Verified identity, least privilege

Access requires a properly verified sign-in. The system reads data with read-only, least-privilege access and never reaches for more than the question needs.

Read-only, scoped access

Everything is auditable

Every question, every line of generated code and every result is recorded — with who asked, under what access, which option handled it and where. A complete, durable trail.

How it works

From question to auditable answer

Four steps, every time — with the boundaries set before any data is touched.

1

You ask

A question in plain language. Off-topic requests are turned away before any work begins.

2

Your scope is set

Your data boundary is resolved from your verified identity and pinned for the conversation — never taken from the request itself.

3

It reasons in a sandbox

The analyst writes and runs code over a de-identified slice, reads its own results, corrects itself, and iterates until the answer holds up.

4

You get the answer

A number, an interactive chart, the code behind it, the as-at date and any caveats — all recorded for audit.
